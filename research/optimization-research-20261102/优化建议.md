# 下一轮优化建议：保持 FP32，减少执行开销

依据：2026-11-02 固定主分支 `e0e39dfb246ccb55efc9424d308db8cfccf5a2a5` 的 submission/solution.py、models/progen/modeling_progen.py；本地官方题包 public_test.py、INTERFACE.md、模型 config.json；本轮 V4 归档与用户提供的同机 FP32 对照截图。本轮对照压缩包尚未收到，前版数值来自截图。

## 当前事实

- RoPE 预计算、torch.compile、KV 预分配已实现，不再把它们当作全新方案。
- V4 的 FP16/all 在 DCU 四项一致率为 0.39%、16.02%、1.37%、7.42%；当前配置不采用。不能外推所有混合精度都失败。
- 同机 FP32 前版截图四项均 100%，耗时 2.2649 / 2.8049 / 5.4859 / 0.7584 秒；新配置 2.3887 / 2.9448 / 5.8598 / 0.7525 秒。各一轮，未证明稳定性能差异。
- 旧 cProfile 采集在早期模型上，包含加载与预热，不是最新 FP32 编译模型的 DCU kernel 分解；不能用旧的 12 秒位置表累积耗时推断今天的瓶颈。

## 调用关系

```text
官方 public_test.py
  load_solution -> Solution.__init__：加载模型并建立 compile 包装
  每个负载：reset -> generate(预热输入) -> 同步
            reset -> 开始计时 -> generate(正式输入) -> 同步 -> 结束计时

Solution.generate
  编码前缀 -> 首次 model(完整前缀，无旧 KV)：prefill
  取最后位置 logits -> 按固定顺序筛选20种字母 -> argmax
  后续 model(新 token，旧 KV)：decode -> 重复选字母
  最后一次性搬回 CPU 并转为字符串

模型内部
  ProGenForCausalLM.forward -> ProGenModel.forward -> 27个 ProGenBlock
  每块 LayerNorm 的同一输出 -> Attention 与 MLP -> 合并残差
```

generate 的循环内没有每步 .cpu()，没有每步 .item()；已有 inference_mode/eval/use_cache。无需重复建议这些已做的工作。lm_head 只有32个词项，不应套用数万词表模型的优化优先级。

## 1. 首选研究方向：编译完整“单步生成”

代码位置：solution.py:56 只编译 self.model；99—113 是模型、候选筛选、argmax 和 KV 接续。
把 model forward + 固定20种候选筛选 + argmax + ID映射包装为 decode_step，再编译这个函数；prefill 单独处理。保留贪心规则及并列时的原顺序，不使用 gpt-fast 的随机采样。

目的：减少编译边界外每步的 Python/小算子调度；每次请求有64—512个生成步骤。是否成为主要收益仍需设备时间线验证。
实现时从未编译的基础模型建立完整 step，避免只是把现有 compiled model 再包一层。fullgraph 可用于检查这个边界是否完整捕获，并不表示整个生成循环已消失。

关联 KV：modeling_progen.py:224—233 仍携带 Python cur_len、变长切片。容量预分配不等于读取形状固定。
若实测表明 guards/recompile 或调度明显，再研究位置 Tensor、固定容量/长度分桶、固定形状掩码。不能简单把1024个位置全算一遍就保证快：短上下文可能增加计算；未写入的缓存不能作为有效输入，也不能让未初始化/NaN区域污染计算。每个请求独立覆盖有效内容。

来源：
- [gpt-fast generate.py](https://github.com/meta-pytorch/gpt-fast/blob/main/generate.py)：独立 prefill/decode_one_token，编译单步函数。
- [gpt-fast model.py](https://github.com/meta-pytorch/gpt-fast/blob/main/model.py)：位置 Tensor、预分配缓存的索引写入。
- [PyTorch 官方说明](https://pytorch.org/blog/accelerating-generative-ai-2/)：分阶段编译与静态缓存，不能将其设备上的倍数迁移到 BW。

## 2. 小改动候选：单 token decode 跳过全真因果掩码

代码位置：modeling_progen.py:129—135。
当前 query长度=1，key/value 已切为有效历史加当前位置。此时最后一行因果掩码全为真，可在这个受限分支跳过因果 mask 切片和 torch.where。
prefill、多 token追加、额外 attention_mask/head_mask 等保留原语义；不取消长度限制。

目的：删掉每层每步不需要的操作，不改变权重、softmax 或累加精度。
风险：编译器可能已优化这些操作，收益可能很小或为零；需要确认生成图及实际测试，不能把源码少一行当作必然提速。

## 3. FP32 矩阵乘自动调优

当前采用 mode=default。单独实验 max-autotune-no-cudagraphs，在现有 FP32 精度设定下让编译器选择矩阵乘实现，避免同时引入图回放与低精度两个因素。
算子调优可能增加大量预热时间，也可能因供应商定制后端受限或形状不利而无收益。必须记录实际选用后端、完整一致性以及编译成本。

来源：
- [PyTorch 2.4.1 mode 定义](https://github.com/pytorch/pytorch/blob/v2.4.1/torch/_inductor/__init__.py)：这个模式只打开 max_autotune，区别于同时打开 cudagraphs 的 max-autotune。
- [PyTorch 2.4.1 compile 文档源码](https://github.com/pytorch/pytorch/blob/v2.4.1/torch/__init__.py)：reduce-overhead 不保证适用，文档对输入修改存在限制。
不能因环境接口叫 cuda 就断言 BW 可直接使用所有 NVIDIA/AMD GPU图回放特性；必须以该 DTK 构建实测为准。不能照日志建议直接开 TF32/high，它改变精度条件。

## 4. ProGen 特有的候选：合并 qkv_proj 与 fc_in

代码位置：ProGenBlock.forward:290—309 左右，Attention 与 MLP 都接收同一个 LN 输出；Attention.qkv_proj 和 MLP.fc_in 可共同投影。

```text
原：h -> qkv_proj -> attention
     h -> fc_in    -> activation -> fc_out

候选：h -> 拼接后的 FP32 Linear -> 拆成 qkv 与 MLP隐藏值 -> 各自后续计算
```

真实尺寸从题包 config 取得：隐藏维1536、27层、16头。qkv_proj输出4608，默认fc_in输出6144，因此合并输出10752。
每层把两次输入投影变成一次，但参数总量和主要乘加总量没有减半。是否更快取决于 GEMM 形状、调度与带宽。
偏置必须正确处理，ProGen的Q/V/K打包顺序必须保持。不同GEMM形状/融合偏置可能改变舍入，FP32也必须重新核验100%输出一致性。此项是由本仓库结构推导出的实验方案，不是外部仓库承诺的收益。

## 后续研究：SDPA / 融合 attention

目前 _attn 是 matmul -> 除scale -> mask -> softmax -> matmul。可探索 SDPA 或定制融合核，但排在上述方向之后。
在 PyTorch 2.4.1 / HIP6.1 / BW 上，FP32能否使用高效后端未验证。math fallback可能数值不同且不更快。
decode的query长度1而key更长，不可盲用is_causal=True：其上左对齐与当前最后位置语义不同。当前有效KV的单token路径不需要因果mask；prefill则保留因果关系。若返回attention权重是外部接口需求，也要保留兼容路径。
- [PyTorch官方因果掩码示例](https://github.com/pytorch/tutorials/blob/main/intermediate_source/scaled_dot_product_attention_tutorial.py)
- [PyTorch2.4.1 SDPA文档源码](https://github.com/pytorch/pytorch/blob/v2.4.1/torch/nn/functional.py)
- [ROCm AITER](https://github.com/ROCm/aiter)：公开硬件支持表不能作为BW兼容证明，暂不建议直接安装替换。

## 建议执行顺序

1. 以通过的FP32版本为基线，先做一次预热后的独立短诊断，区分prefill/稳态decode、CPU调度/设备kernel。若torch.profiler设备事件不可用，明确记录能力限制；cProfile不能替代DCU kernel耗时。
2. 优先测试单步编译或单token mask快路径；每个候选只引入一种主要变化。
3. 若矩阵乘主导，再做FP32自动调优及投影合并；若注意力主导，再评估融合attention。
4. 官方基准与测试器不改；完整四项必须100%，再同机交替复测至少三轮，保留每轮原始值，以中位数和范围报告。三轮只是初筛，微小差异仍需更多重复。
5. 预热/编译总时间另报；计时区内不出现临时新编译。不同输入连续调用验证缓存独立性，不能复用上一请求的生成结果。
