# 贡献确认规则

记录要能回答：谁做了什么、产生什么结果、证据在哪里、谁核验过。记录事实，不预先分配贡献百分比，不按提交次数或代码行数排名。

## 一条有效贡献

必须关联任务编号、具体动作、产出链接、验证结论、本人实际工作、协作人与 AI 协助范围。采用方案、失败实验、定位问题、复现、审查和整理可复现实验材料均可记录。

例如“测试了 BF16”过于笼统；应记录转换修改、对应代码版本、四项时间和一致率、日志位置，以及发现的问题。结果尚未验证时写待验证，不能写提升。

## 确认流程

1. 负责人在自己的成员页添加记录，并关联任务或 PR。
2. 复核人在对应 Issue/PR 或记录中留下核查意见。
3. 证据完整后标为已确认；缺少验证时保留待确认。
4. 合作任务分别说明主导、实现、测试与审查的真实参与，不把全部工作重复算为各自独立完成。

GitHub 账号的提交记录是证据之一。有人代为录入时，写明实际作者和录入人；不要把统一账号的提交数当成人员贡献。

## AI 使用记录

允许记录 AI 辅助解释、生成代码、排查错误和整理文档。本人应写明自己提出的目标、实际修改、运行与验证、能解释的内容；不要把 AI 生成且未理解、未验证的工作写为独立研发。

本次协作体系由 Codex 协助起草，依据用户确认的三人新手情况设计。建立这些模板不计为 A、B、C 已完成模型开发或实验。

## 最终报告汇总

从三人的已确认记录提炼实际分工。对于未采用的优化、尚存限制、未完成实验和第三方代码来源如实说明。需要贡献比例时，由三人基于证据协商确认，模板不自动给出比例。

## 本地、DCU 与审查的证据类型（2026-10-29）

分别记录：代码实现、本地独立执行、本地原版/候选比较、指定 DCU 执行、代码审查、材料核对与失败定位。其他人提供命令、由用户上 DCU 执行时，分别记录设计与实际执行，不把两人都写成独立 DCU 复现。

队友能用不同 AI 工具协助小任务，模型输出需核查；不以工具品牌、付费档位或代录提交数分配贡献。负责验证的人可以产出适配代码、边界检查和错误定位，不固定为只写报告。
