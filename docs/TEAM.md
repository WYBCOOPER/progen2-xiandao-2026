# 三人分工与每日协作

大家均为新手，先共同跑通，再按小任务分工。角色表示负责把事情推进完成，不表示只能由一个人做，也不代表已有相应技术能力。

| 成员 | 主线 | 第一项交付 | 后续技术任务 | 固定复核人 |
|---|---|---|---|---|
| A | 环境与程序集成 | DCU 环境信息、运行命令与基准完整日志 | 理解并完成模型加载，整合通过验证的修改 | C |
| B | 生成流程与优化 | 解释前缀如何变成新字母，标注基准生成流程 | 实现生成接口，选一个缓存或流程优化做对照 | A |
| C | 测试与结果分析 | 解释四项负载和 JSON 字段，核对基准结果 | 整理实验数据、定位一致性差异、协助性能分析 | B |

三人都要读基准、执行或复核实验、说明自己负责的代码。报告由各人写自己实际完成部分，A 负责汇总，B 和 C 复核。不能把一人固定为只写报告。

## 共同先学的最小内容

1. 前缀是输入；每次输出一个字母，加入上下文后再预测下一个。
2. Prefill 是首次处理前缀，Decode 是后续逐步生成，KV 缓存减少重复计算。
3. FP32 是参考计算精度；降低精度可能更快，也可能改变输出，必须实测。
4. 四项测试的 B、L、G 不同；加速比必须比较相同任务与设备。

每人能用自己的话解释以上流程即可进入实践，不要求先学完整深度学习课程。

## 每日十分钟同步

每人回答：交了什么（附链接）、当前卡在哪里、下一个可交付物是什么。卡点连续 30—60 分钟没有进展时，在任务中贴完整报错、已尝试方法和需要的帮助，不等到截止日。

每人同时最多推进一个主要任务。由 A 维护 DCU 使用时段，正式测速时同一设备不并行运行其他任务。主线依赖环境时，B 可先读代码，C 可先准备结果说明。

## 改代码的方法

各人使用自己的 GitHub 账号和任务分支，例如 a/environment、b/generation、c/results。通过 Pull Request（修改申请）说明变更与验证，由另一人复核后合入。不要三人同时覆盖同一份 solution.py；需要共同修改时约定一人执笔，另两人记录各自实际工作。

首次先追求完整、正确、可复现。之后每次只验证一个优化假设。FP16/BF16、量化、自定义算子均为待实验方向，不提前承诺速度或一致性。
