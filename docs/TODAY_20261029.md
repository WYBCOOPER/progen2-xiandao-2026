## 理解达到什么程度才进入改动

每人都应能指着真实代码解释以下关系，不要求先学完 Transformer 或独立发明优化：

1. 模型在 __init__ 中加载，FP32 在哪里设置；加载不计入官方生成时间。
2. 第一轮传完整前缀，后续轮次传新 token；能够指出 next_input 的两次赋值。
3. 从允许的 20 种氨基酸选最高分，规则不随优化改变。
4. past_key_values 在哪里传入、更新；它与输入相关，新请求必须独立。
5. generate 返回新生成后缀，条数、长度、顺序与输入要求一致。
6. 本地开发检查与 DCU 官方验收分别证明什么，不能互相代替。

实现位置表的人还要说明位置、形状、精度、设备与缓存失效条件；负责验证的人要解释先前缀后新 token、不同输入和长度变化时怎样发现问题。解释附代码位置，并注明 AI 协助和仍不确定的部分。

## 本地 N 卡怎样复用官方测试

官方 public_test.py 的运行入口会检查 torch.version.hip，CUDA 版 PyTorch 不能直接通过这个入口。新建 dev/local_test.py（本次已提供初版，待本地 GPU 实测），引用题包中已有的加载、输入/输出检查及比较逻辑，单独组织本地运行；保留官方测试器、环境检查和参考输出原样。

本地先验证开发入口在未修改版本上能工作，再比较同一台机器、同一环境的未修改版与候选版。记录精度、软件版本、输入、生成长度、输出差异与错误。第一步可以用小批量短生成排错，再扩展检查；短测试不代表四项完整通过。本地原版不保证与 DCU 原版逐字相同，跨设备差异先与改动影响分开。

dev/local_test.py 重点检查：输出格式、相同输入重复调用、同一对象不同输入 A→B→A、不同合法长度和 batch、缓存重置。本地结果放 local_results/ 并标 purpose=local_development，不能标为官方成绩。若复用到的函数未完整覆盖某项检查，在脚本说明中明确补充和缺项。

本地只证明本地可运行和局部正确性；本地更快不证明 DCU 更快。GPU 专用算子、编译和低精度尤其要重新检查 DCU 支持与结果。两边分别配置 CUDA/HIP 环境，不照搬整套安装包，不凭模型品牌或显卡名称预填成功。

## 验证与组合顺序

本地原版 → 本地单项候选 → DCU 原版对照 → DCU 单项候选 → 另一项也独立通过 DCU → DCU 组合。

有 A/B 两项时保留“原版、仅 A、仅 B、A+B”的独立版本和结果。每种都检查四负载的格式、一致率和 time_s；组合不是简单相加，单项通过不等于组合正确。收益接近波动时补多轮完整对照，最终记录仍为最终代码对应的一轮完整测试，不能拼最好值。

只有你在同一 DCU 实例上顺序运行，队友可以同时读代码、修改、分析。不要在正式测速期间占用同一设备跑其他任务。Python 调用诊断包含的加载/等待不等于 DCU 算子占比，信息不足就记录待进一步测量。
